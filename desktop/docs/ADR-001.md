# ADR-001: Qt 6 hybrid port of OctoBeat

- **Status:** accepted, playback section superseded
- **Date:** 2026-11-19
- **Update 2026-11-21:** libVLC was replaced by the native Rust engine
  (`rust/audio-engine`: Symphonia + `symphonia-opus` + cpal). The engine runs
  in a decoder thread with a lock-free ring buffer; the C++ UI talks to it
  through the C ABI in `desktop/src/audio/audio_engine.h`.
- **Deciders:** ukimaka, OpenCode
- **Supersedes:** none

## Context

OctoBeat is a ~27k-line Python/PyQt5 desktop music player. The goals of the port are:

1. remove the Python runtime from the application;
2. improve startup time and memory use;
3. keep the existing functionality and visual style, with only small visual losses allowed.

The current app uses PyQt5 Widgets, libVLC through `python-vlc`, SQLite, `mutagen`, `ffmpeg`, LRCLIB, MPRIS, a system tray, a mini-player, karaoke/lyrics overlays, a trim editor, and YouTube downloads through `yt-dlp` + SomeDL.

## Decision

Port the application as a **C++20 / Qt 6 Widgets UI with a Rust core**.

- **UI:** C++ Qt Widgets, translated 1:1 from the existing PyQt5 code. QSS themes, custom delegates, drag & drop, rich text and native dialogs stay in Qt.
- **Core:** Rust owns the database, metadata/tags/covers, library scanning, lyrics, downloads, playback controller (queue, shuffle, repeat, crossfade state), profile statistics, dependency management and updater logic.
- **Playback engine:** a native Rust engine (Symphonia + Opus + cpal) behind a
  small C++/Qt adapter. Decoding and output live on engine threads; position,
  duration, pause, seek, volume and crossfade are exposed as Qt signals.
- **Downloads:** `yt-dlp` and SomeDL remain self-contained sidecar binaries. The main application does not require Python, pip or a virtualenv. Porting SomeDL's metadata enrichment to Rust is a later, separate decision.
- **Configuration:** QSettings remains the source of truth for v1. C++ reads it and passes a snapshot to Rust; changes are pushed to the core. A Rust-owned config file can replace it after cutover.
- **Data:** the existing SQLite schema is preserved. Migrations are ported 1:1. The first Rust run creates an automatic database backup. Beta builds use a copy of the database, not the user's live file.
- **Platforms:** Linux (Flatpak + AppImage) and Windows (Inno Setup) for v1. macOS is out of scope until the Linux/Windows port is stable.
- **Toolchain:** Qt 6.5+ (target 6.8 LTS), CMake + Corrosion, C++20, Rust 2024, GPLv3-compatible dependencies, vendored crates for Flatpak.
- **Repository layout:** the existing Python app stays at the repository root and on `main`. New Rust code lives in `rust/`; the C++/Qt UI and packaging live in `desktop/`. Shared `assets/`, `themes/` and `icons/` remain at the root until cutover.
- **Branching:** all port work happens on `rust-port` (a git worktree). `main` remains the stable Python app. New features are frozen during the port; critical fixes are cherry-picked.

## Architecture

```
┌────────────────────────── C++20 / Qt 6 Widgets ──────────────────────────┐
│ MainWindow · Library · Playlists · PlayerBar · Settings · Profile ·      │
│ Lyrics · MiniPlayer · Dialogs · Tray · MPRIS · AudioEngine (native)       │
└───────────────▲──────────────────────────────────┬───────────────────────┘
                │ events (Qt signals / queue)       │ commands (cxx)
┌───────────────┴──────────────────────────────────▼───────────────────────┐
│ Rust core                                                                 │
│ db · tags/covers · scanner/watcher · lyrics · downloads · playback       │
│ controller · profiles · updater · deps · logging                         │
└───────┬───────────────────┬───────────────────┬──────────────────────────┘
        │                   │                   │
   SQLite (rusqlite)   native AudioEngine  yt-dlp / SomeDL / ffmpeg
                       (Symphonia+cpal)    (sidecars, CLI)
```

### Bridge

- `cxx` bridge with one opaque `Core` object.
- C++ → Rust: commands (`scan`, `play`, `queue_add`, `download`, `search`, ...).
- Rust → C++: events (`track_changed`, `state_changed`, `position`, `duration`, `scan_progress`, `download_progress`, `error`) delivered through a thread-safe queue. The UI drains it on a `QTimer` (50 ms) or via `QMetaObject::invokeMethod`.
- Rust owns a tokio runtime, SQLite and background work. C++ owns Qt objects, QSettings, the AudioEngine wrapper and rendering.
- QSettings is read by C++ and passed to Rust as a `CoreConfig` snapshot. The bridge pushes updates when settings change.
- Paths are resolved with `QStandardPaths` in C++ and passed to Rust, so platform path logic is not duplicated.
- Logging: Rust `tracing` and C++ `qInstallMessageHandler` write to one log file.

## Tooling: rust-anything

`rust-anything` 2.0.2 is used for **unit-level behavior recording**, not for whole-app scaffolding.

- Each core unit is bridged to a PyO3 crate under `rust/<unit>-rs`.
- `record` captures the original Python behavior on generated edge cases plus real-world inputs in `custom_cases.jsonl`.
- The Rust port is written in `src/port.rs`; `diff` replays every case; `gate` requires fmt, clippy, tests, API completeness and 100% behavior match.
- This gives a proven parity suite for `db.py`, `metadata.py`, `lyrics_api.py`, `controller.py`, etc.
- `app_front_door` / `app_lift` are deliberately not used: the target UI is C++/Qt, not a pure Rust CLI/server.

The first pilot ported `metadata_normalize.py`:

- 5 public functions;
- 1316 recorded cases;
- 1316/1316 match;
- `gate` passed.

See `desktop/docs/PILOT-001.md`.

## Consequences

- The project is now two-language. The C++/Qt UI port is the largest single work item.
- The port is measured in months, not weeks. The core can be proven incrementally; the UI remains a manual, screen-by-screen effort.
- Sidecar packaging for Flatpak and Windows needs explicit work.
- Existing user data can be preserved: SQLite, QSettings, profile assets, covers and cookies.
- The Python app remains runnable and is the behavioral oracle until cutover.
